# BruteForce：全量打分为何仍是重要基础

[直观图解](visual_guide.md)

配套：[代码逐段导读](code_walkthrough.md) · [索引总览](../README.md)

## 1. 解决的问题

给定 N 条向量、查询 q 和 k，直接计算所有有效向量与 q 的距离，再保留最近的 k 个。它消除了“候选有没有被搜索到”的问题，是理解其他索引和生成稠密精确基准的起点。

当输入和内部编码均保持 FP32，使用相同距离定义且不启用会提前截断的限制时，可用它作为近似索引的对照。若内部量化成 SQ/PQ 等有损编码，虽然仍扫描所有记录，排序已不保证等同原始 FP32。

## 2. 数据结构

| 组件 | 作用 | 为什么这样设计 |
| --- | --- | --- |
| `inner_codes_` | 保存向量或多向量编码并执行 Query | 扫描循环不必感知具体编码方式 |
| `label_table_` | 外部 label 与内部槽位映射 | 允许业务 ID 不连续，底层仍按紧凑编号访问 |
| `total_count_` 等计数 | 管理已使用槽位与删除数量 | 区分物理记录和逻辑有效记录 |
| 结果堆 | 保留当前最优候选 | 无须保存全部 N 个距离并完整排序 |
| `global_mutex_` | 协调搜索与修改 | 强制删除搬移槽位时避免读到不一致数据 |

数据单元在概念上扁平，不意味着底层必定是一段连续 malloc 内存；实际可使用块式存储。

## 3. 构建过程

`Build` 先 `Train` 再 `Add`。Train 对不需要训练的编码基本不承担模型学习，而训练型量化器会准备编码参数。Add 检查输入类型与 ID，分配槽位，写入编码与可选属性，并维护计数和失败 ID。

**设计原因：** 不建立额外导航结构，使写入成本主要落在编码与存储上。**代价：** 所有筛选工作都推迟到查询，数据越大，扫描越贵。

## 4. 搜索过程

```text
准备查询 Computer
  → 组合删除 / ID / 属性过滤
  → 遍历有效内部 ID
  → 普通路径逐记录调用 inner_codes_->Query；自定义距离路径可批处理
  → 将满足条件的结果插入有界堆
  → 合并线程结果（若启用扫描并行）
  → 转换外部 ID，返回距离有序结果
```

按距离升序返回最近邻时，保留最优 k 个的结构通常把“当前最差保留项”放在堆顶，这样遇到更好的项就可以淘汰它。不要只根据中文“小顶堆/大顶堆”术语猜行为，应看 `DistanceHeap` 的模板参数、比较器和调用点。

对普通稠密输入，打分成本约 O(ND)，有界堆维护可按 O(N log k) 理解；批处理、过滤、SIMD 和并行会改变实际常数。若扫描受内存带宽限制，线程数增加不一定线性提速。

## 5. 为什么复用 DataCell 而不直接写点积循环

同一遍历过程可以切换 FP32、量化编码或多向量打分。算法复用有效 ID 扫描、过滤、堆和结果转换；DataCell 处理每条记录的实际含义。WARP 就是这种复用的具体例子。

其代价是阅读一次距离计算需要继续跟进 `FactoryComputer` 和 `Query`，不能只看 BruteForce 文件。

## 6. 删除与更新

标记删除隐藏 ID，保留存储；强制删除在适用配置下压紧槽位，并更新被搬移记录的 label 映射。属性过滤开启时存在删除限制；多向量模式也不能直接套用单向量强制删除能力。

单向量 `UpdateVector` 可以覆盖编码，因为没有需要修复的图边。这解释了为什么同名更新操作在 BruteForce 中相对简单，而在 HGraph 中可能需要处理邻居关系。

## 7. 参数如何影响设计

- `base_quantization_type`：选择扫描对象的表示精度与体积。
- `parallelism`：分配单查询扫描的线程资源；它影响吞吐与单查询延迟的平衡。
- `resize_increase_count_bit`：按批次扩容，减少频繁分配，但可能保留更多空闲槽位。
- `use_attribute_filter`：引入属性索引和过滤执行开销，并改变部分操作约束。

## 8. 应当带着什么问题读代码

为什么 Build 必须先 Train？一个槽位写入失败时 ID 怎么处理？过滤发生在距离计算前还是结果入堆前？不同分支是否相同？物理删除后为什么不能只递减 `total_count_`？
